# 内核与插件规范 3.0（跨平台）

> **用途**：给 Linux / macOS 端开发者（或其 AI agent）一份**可直接开工**的规范：
> 内核是什么、插件能做什么、契约怎么切、界面怎么挂、权限怎么判、跨平台要注意什么、怎么验收。
>
> **定位**：v2（`docs/plugin-spec-v2.md`）定义**外部插件**的包结构 / 权限 / 声明式 UI；
> 本文定义**内核 + 插件模型本身**，是 v2 的超集：内置插件与外部插件都按本文登记、都走同一套贡献点。
> 六端（Windows / 鸿蒙手机 / 鸿蒙 PC / Android / Linux / macOS）**共用这一份规范**。
>
> **状态（2026-10-15）**：本文的 Windows（C#）参考实现已落地 P0；Linux/macOS 端按本文实现时，
> 请对照 §13 验收清单逐项打勾，§14 是已经踩过的坑（照着避）。
>
> 关键词：**必须（MUST）** / **应当（SHOULD）** / **可以（MAY）**。凡"必须"项，端口实现要能通过 §13 的对应用例。

## 0. 开工必读（先看这一页）

这一节是给端口开发者的**前置提醒**：看完就可以直接按 §1 往下做，不需要再问。

### 0.1 别把参考实现当成"已验证"

参考实现（Windows / C#）只落地了 P0 的一部分。**§附录 B.1 是逐条状态表**，凡标
"未实现 / 部分"的条目，都是**规范要求但参考实现还没做**——端口要按规范做，不要照抄现状。
最容易踩的三条：

1. **上下文里的调度器（§7 `scheduler`）参考实现没有**：端口**必须**注入，否则插件只能自己起线程，
   停用时收不回来。
2. **`requires` 契约依赖与反向级联停用参考实现没有**：这是 §5.6 的强制项，别以为"已经有 depends 就够了"。
3. **config/data/cache 三根参考实现只有一个根**（Windows 历史兼容）：Linux/macOS **必须**分三根（§11.1）。
4. **外部（沙箱）插件系统与内核尚未合并**：v2 的沙箱（Jint/Python、权限白名单、声明式 UI）
   目前独立运行，贡献点还没统一进内核的贡献表。端口要么先只做内置插件，要么在实现时**一步合并**
   （推荐后者：两套并存越久越难拆）。

### 0.2 七条禁令（违反即返工）

1. 内核里**不许**出现业务名词（下载/账户/版本/助手…）——出现就是分层错了。
2. 契约**不许**用具体类；只有"能被换实现"的才配叫契约。
3. 插件**不许**碰全局单例；一切经上下文（§7）。
4. 插件**不许**自己起线程/定时器/事件循环；一律用宿主注入的调度器（§11.3）。
5. 插件**不许**直接操作视图树；只能注册贡献点（§8）。
6. **不许**在 manifest 或路径处理里出现绝对路径、反斜杠、系统 locale 相关的比较（§11.1）。
7. 自绘界面**不许**硬编码颜色/圆角，必须查令牌（§8 + 引擎需求 N7）。

### 0.3 开工前必须拍板的两件事（宿主侧决策，不是实现细节）

| 决策 | 选项 | 建议 |
|---|---|---|
| 外部（沙箱）插件能否**提供契约实现**（跨沙箱边界） | ① 不支持，只支持进程内 ② 支持，定义跨边界 C ABI/消息契约 | **选 ①**：先只支持进程内形态；跨边界单独立项，成本与风险都高一个量级 |
| 是否**动态加载原生插件**（.so/.dylib） | ① 只编译期内置 ② 开放动态加载 | **选 ①**：内置插件编译期登记，零 ABI 问题；确有需求再按 §11.4 的 C ABI 规范单独立项 |

这两条一旦选了，**不要中途改**——它们决定 §9 的信任边界与 §11.4 的 ABI 要求。

### 0.4 Linux / macOS 上最容易翻车的三处

| 坑 | 说明 | 对策 |
|---|---|---|
| **大小写** | Linux ext4 敏感、macOS APFS 默认不敏感；同一个插件 id 写成 `StarCloud.Download` 在两端行为不同 | 插件 id、目录名、契约名统一小写；比较一律序数（§11.1） |
| **路径根** | Linux 用 XDG 三根、macOS 用 `~/Library/*`；程序安装目录只读（包管理器 / bundle） | 一切写入走注入的三根；**禁止**写安装目录（§10、§11.1） |
| **事件循环** | 两端主循环完全不同（GLib / libdispatch / NSRunLoop），且可能没有"UI 线程"概念 | 内核只拿调度器句柄，**禁止**假设主线程（§11.3） |

### 0.5 怎么算做完

- 对照 **§13 验收清单逐项打勾**，每项都要有自动化用例（不接受"手工试过"）。
- 出问题先查 **§14 已知坑**；那里每条都是真实踩过的。
- 与 UI 引擎的分工看 **§15**：插件模型是宿主的事，引擎只提供视图树/挂载位/令牌。
- 端口的目录与接口形状见 **§12**；参考实现的文件地图见 **附录 A**。

## 1. 术语与分层

| 术语 | 含义 |
|---|---|
| **宿主 Host** | 一个具体的软件（启动器、工具、编辑器……）。宿主拥有业务、装配界面、决定装哪些插件。 |
| **内核 Kernel** | 宿主里的最小地基：设置与路径、日志、事件总线、服务注册表、插件宿主、贡献点注册表。**不含任何业务**。 |
| **外壳 Shell** | 内核的一部分但不属于功能：窗口、导航、页面宿主、浮层、通知、主题、多语言、动效档位。 |
| **插件 Plugin** | 一切功能。分两种信任等级：**内置**（进程内、完全信任）与**外部**（沙箱 + 权限白名单）。 |
| **契约 Contract** | 一个**接口（能力）**，如"下载引擎""投影解析""LLM 网关"。插件注册实现，别的插件按契约取用。 |
| **贡献点 Contribution** | 插件挂到宿主界面上的东西：导航项、页面、卡片、分区、插槽、浮层。 |
| **模块描述符 Descriptor** | 一个插件的清单：id / 名称 / 版本 / 种类 / 提供什么 / 依赖什么 / 怎么激活 / 要什么权限。 |

分层与依赖方向（**MUST**）：

```
外壳 Shell      导航 · 页面宿主 · 浮层 · 主题令牌 · 多语言 · 动效档位
   ↑
内核 Kernel     设置/路径 · 日志 · 事件总线 · 服务注册表 · 插件宿主 · 贡献点注册表
   ↑（只通过 IPluginContext）
插件            引擎类 · 功能类 · 助手类 · 界面类（内置 = 进程内；外部 = 沙箱）
```

- 插件之间**MUST NOT** 直接引用对方的类型或实例；只能 ① 按契约取用 ② 收发事件。
- 内核**MUST NOT** 出现具体功能名（下载、账户、Nova、版本…）。内核里出现业务名词 = 设计错误。
- 外壳**MUST NOT** 被插件直接操作；插件只能通过贡献点注册表声明界面。

**判据**：没有它插件就跑不起来的东西是内核；只要有插件可以不做它，它就是插件。

## 2. 五条铁律（违反即回退）

1. **可逆**：任何插件的启用/停用必须可逆。停用后：契约注销、贡献撤下、事件订阅断开、
   数据文件不动。**再次启用必须能回到与首次启用完全一致的基线**（不能重复注册、不能残留视图）。
2. **不阻塞**：激活/停用**MUST NOT** 在 UI 线程上做 I/O 或长计算；有 I/O 的插件**必须**声明 `lazy`
   或在激活时把工作丢给调度器。宿主同步启动内核时，只允许纯内存构造的插件保持 `eager`。
3. **不假设**：内核与插件**MUST NOT** 假设特定 UI 工具包、事件循环、线程模型、文件路径或语言运行时。
   这些一律由宿主注入（§7、§11）。
4. **不越权**：外部插件只能经由其 manifest 声明的权限访问宿主能力；内置插件虽完全信任，
   **也 MUST 登记权限声明**（用于审计与将来收紧）。
5. **契约即能力**：只有"能被换实现"的才配叫契约，契约**必须是接口/纯虚接口**，
   **MUST NOT** 用具体类当契约（例外见 §5.4 过渡条款）。

## 3. 模块描述符（Descriptor / manifest）

内置插件在代码或随程序集附带的 JSON 里声明；外部插件用 `manifest.json`。
**两者字段同名同义**（v2 §3 是外部插件的完整版，本节是内核需要的最小集）。

```jsonc
{
  "id": "starcloud.download",          // 必填。全局唯一，反域名或 <vendor>.<feature>；
                                        // 只允许 [a-z0-9._-]，长度 3..64，大小写敏感比较但 MUST 小写登记
  "name": "多线程下载引擎",             // 必填。展示名（可多语言）
  "version": "1.0.0",                  // 必填。语义化版本
  "apiVersion": "3.0",                 // 必填。编译/加载时校验（§5.5）
  "kind": "engine",                    // 必填：engine | feature | assistant | ui
  "builtin": true,                     // 内置插件为 true；外部插件缺省 false
  "activation": "eager",               // eager | lazy（缺省 eager）
  "provides": ["IDownloadEngine"],     // 本插件对外提供的契约名（懒激活与"谁能提供"查询用）
  "requires": ["IDownloadEngine"],     // 本插件**消费**的契约名（**必填**，只要你 Get 了就必须声明）：
                                        // 内核据此在激活前确保提供者可用，缺了直接 Failed 并说明缺什么，
                                        // 而不是等某次调用才在运行时炸（详见 §5.6）
  "depends": { "starcloud.settings": "^1.0.0" },  // 依赖**插件 id** → 版本范围（同样由客户端自动处理）
  "conflicts": { "com.example.other": "*" },      // 冲突声明（命中则不激活）
  "permissions": ["net.http", "fs.write:launcher"],   // 权限（§9）
  "essential": false,                  // 内核必需插件：不允许用户禁用（缺省 false）
  "contributes": { ... },              // UI 贡献（§8；外部插件的完整语法见 v2 §6）
  "description": "…", "author": "…", "homepage": "…", "license": "MIT"
}
```

规则（**MUST**）：

- `id` 全局唯一；重复登记 → **拒绝第二个并报错**（不许静默覆盖）。
- `kind` 决定激活次序（§4.3），`provides` 决定懒激活时"谁能提供"，`depends` 决定拓扑次序。
- `depends` 的版本范围采用 npm 风格（`^1.0.0`、`>=2 <3`、`*`）；解析失败按"依赖不可用"处理。
- 描述符**不得**包含绝对路径、平台专有分隔符（一律 `/`）或本地化文案数组（多语言走 i18n 表）。
- 内置插件的 `version` 与内核 `apiVersion` **MUST** 一起进构建信息，便于诊断。

### 3.1 能力矩阵（插件能做什么）

| 种类 `kind` | 典型 `provides` | 典型 `contributes` | 典型权限 | 例子 |
|---|---|---|---|---|
| `engine` | 1 个引擎契约（下载 / 投影 / LLM / 链路 / 渲染） | 可能挂设置分区 | `net.http`、`fs.*` | 多线程下载引擎 |
| `feature` | 0–n 个领域契约 | 导航项 + 页面 + 设置分区 | 按功能 | 版本管理、存档库、账户 |
| `assistant` | `INovaAgent` / `INovaTool` | 导航项 + 页面（对话/工具） | `ai.llm` | Nova 对话、Nova 执行器、单个工具 |
| `ui` | 无 | 卡片 / 分区 / 插槽 / 浮层 | `ui.notify` | 纯展示类扩展 |

- 一个插件**可以**跨种类（例如既是 `engine` 又挂设置分区），但 `kind` **MUST** 填它**最主要**
  的那一个——它决定激活次序（引擎先于依赖它的功能）。
- "每个工具一个插件"是**推荐**形态（可单独启停、可被替换），不是强制：
  小工具可以合并成一个插件，只要它们共享同一份依赖与权限。
- 插件**MUST NOT** 在自己的 UI 里直接读宿主服务的状态并缓存（用契约 + 事件），否则停用后会残留。

## 4. 生命周期

### 4.1 状态机

```
Registered ──activate──▶ Activating ──▶ Active ──deactivate──▶ Stopped
    │                        │                                   │
    │                        └──异常──▶ Failed（本次运行内不可再激活）
    ├──Disabled（用户/配置禁用，激活请求直接拒绝）
    └──（依赖不可用 / 冲突命中）──▶ Failed，并记录原因
```

- 状态变化**必须**可观测（事件或回调），插件页/诊断要能显示：状态、错误、激活耗时。
- `Failed` 在**本次进程内不再自动重试**；用户显式"重试"才允许重置为 `Registered`。
- `Stopped` 可以再次激活（必须回到基线，见铁律 1）。

### 4.2 激活/停用算法（**MUST** 按此顺序）

```
Activate(id):
  1. 查状态：Active 直接返回成功；Disabled/Failed 返回失败；Activating 返回失败（环保护）
  2. **先置 Activating**            ← 必须在递归依赖之前，否则 A→B→A 会无限递归到栈溢出
  3. 逐个依赖：不存在 → Failed；依赖 Failed/Disabled → Failed；
               未激活 → 递归 Activate(依赖)，失败则本插件 Failed
     ※ 第 3 步只是 `depends`（插件依赖）。`requires`（契约依赖）、`conflicts`、循环检测
       在 §5.6.2 有完整算法，实现时把两节合并成一段流程（推荐以 §5.6.2 为准）。
  4. 构造上下文（§7），实例化插件，await InitializeAsync/initialize(ctx)
  5. 成功 → Active + 记录激活耗时 + 发 PluginActivated 事件
     异常 → Failed（保留错误信息）+ 发 PluginFailed 事件（不得让异常冒泡到宿主启动流程）

Deactivate(id):
  1. 只处理 Active；先标记 Stopping（阻止新订阅/新贡献）
  2. 调 ShutdownAsync/shutdown()（插件释放自己的资源；可抛异常，内核吞掉并记日志）
  3. 内核统一收尾，顺序固定：**撤贡献 → 注销契约 → 断开代管订阅 → 清实例与上下文**
  4. Stopped + 发 PluginDeactivated 事件
```

### 4.3 激活次序

按 `kind` 升序：`engine(0) → feature(1) → assistant(2) → ui(3)`；同种内按登记顺序；
依赖由 §4.2 递归保证**先于**被依赖者。停用按激活的**逆序**。

### 4.4 懒激活（**MUST**）

- `activation: "lazy"` 的插件在启动时**MUST NOT** 激活。
- 触发点：有人按契约取用且注册表里没有该契约时，查 `provides` 找到唯一提供者并激活它，再取一次；
  仍然取不到则报错（错误信息要带"提供者是谁、当前状态"）。
- 懒激活**MUST** 是幂等且线程安全的；**MUST NOT** 在 UI 线程上阻塞等待 I/O
  （宿主提供异步取用接口，或懒插件在激活时把 I/O 交给调度器）。
- 环保护：`Activating` 状态下再次被请求激活 → 立即返回失败（防止递归）。

### 4.5 失败隔离

- 单个插件激活失败**MUST NOT** 阻止其它插件激活，也**MUST NOT** 阻止宿主启动
  （除 `essential` 插件失败：宿主可以选择提示后退出）。
- 依赖失败的插件标记 `Failed` 并给出可读原因（"缺少依赖 X" / "依赖 X 激活失败"）。

## 5. 契约

### 5.1 切分原则

- 按**能力**切，不按现有类切。判据：**存在第二种实现的可能**。例：
  `IDownloadEngine`（换并发策略/换协议）、`IProjectionEngine`（换渲染后端）、
  `ILlmGateway`（换服务商）、`IPeerLink`（换传输）、`INovaTool`（**每个工具一个契约实例**）。
- 契约**MUST** 是接口/纯虚接口，**MUST NOT** 暴露具体实现类型、UI 类型、平台类型。
- 契约**MUST** 自带足够的语义信息：方法/属性要有"线程性、是否阻塞、错误语义"的文档注释。
  返回 `Task`/`future` 的方法默认不阻塞调用线程；同步方法必须标明。

### 5.2 注册与解析语义（**MUST** 一致实现）

| 操作 | 语义 |
|---|---|
| `Add<契约>(实现, priority = 0)` | 登记一条实现，归属"当前正在激活的插件" |
| `Get<契约>()` | 取**优先级最高**的实现；**同优先级时后注册者胜**（这就是"外部/新插件覆盖内置"的机制） |
| `GetAll<契约>()` | 取该契约的全部实现，按优先级降序（多实现场景：资源源、安装器） |
| `TryGet` | 同 Get，但不存在时返回 false 而不抛 |
| 停用插件 | 按归属**批量注销**该插件的全部登记 |
| 快照 | 可枚举全部登记（契约名 / 提供者 / 优先级），供插件页与诊断 |

- 注册表**MUST** 线程安全（插件可能在后台线程注册）。
- 解析**MUST NOT** 触发懒激活（懒激活只发生在内核的 `Get` 壳上，见 §4.4）。
- "当前正在激活的插件"**MUST** 是内核维护的显式状态（栈/字段），**MUST NOT** 依赖线程局部变量
  （激活可能是异步的，会跨线程续跑）。

### 5.3 契约归属

- 契约的**定义**属于宿主（谁需要谁定义），**MUST NOT** 进 UI 引擎（§15）。
- 一个插件可以提供多个契约；一个契约可以有多个实现；**同名契约的"形状"必须由宿主统一定义**，
  插件不得私自扩展接口（需要扩展就提出新契约或新方法 → 走 §5.5 版本化）。

### 5.4 过渡条款（仅限迁移期，**MUST** 标注 TODO 与回收计划）

老代码里服务之间按具体类互相构造（如 `ManifestService(DownloadService, ResourceCacheService)`）。
迁移期允许内核额外提供 `AddBuiltin(具体类型, 实例)` 只做"取回"，**不参与契约解析**：

- 它 **MUST NOT** 被新代码使用；
- 它 **MUST** 在迁移完成后删除；
- 端口实现可以选择不提供这个口子（推荐不提供，直接一步到位）。

### 5.5 版本化

- 内核声明 `apiVersion`（如 `3.0`）。插件 manifest 声明自己适配的 `apiVersion`。
- 兼容规则：**同主版本内允许新增契约/新增可选方法**；**删除/改签名 → 主版本 +1**。
- 内核加载插件时**MUST**校验：主版本不一致 → 拒绝加载并给出明确错误（不要"尽力而为"）。

---

### 5.6 依赖声明与自动处理（**MUST**）

插件**MUST** 在 manifest 里声明两类依赖，**客户端（内核）MUST 自动处理**——插件不许自己去找
提供者、不许自己 new 别人的实现、不许在代码里硬编码"用哪个插件"。

#### 5.6.1 两类依赖

| 声明 | 含义 | 例子 |
|---|---|---|
| `requires: [契约名]` | "我运行时要按契约取用这些能力" | `["IDownloadEngine", "ITranslationEngine"]` |
| `depends: { 插件 id: 版本范围 }` | "我需要某个**具体插件**在场（且版本满足）" | `{"starcloud.settings": "^1.0.0"}` |

- 只要插件代码里 `Get<T>()` 了某个契约，**MUST** 在 `requires` 里列出它。
- `depends` 只用于"必须是我指定的这个插件"的场合（例如插件 A 是插件 B 的配套 UI）。
  仅仅需要能力时用 `requires`，**不要**用 `depends` 绑死具体插件（那会阻碍替换实现）。
- `requires` 与 `depends` 都**MUST** 参与激活前的解析，不允许"先激活，等用到再发现缺"。

#### 5.6.2 激活前解析（客户端自动做）

```
Activate(P):
  1. 状态检查（见 §4.2），置 Activating
  2. depends 解析：每个 插件id → 必须存在且版本满足；不存在/版本不满足 → P 置 Failed（原因写清）
                   版本不满足 → 不激活、不降级（不许"凑合用"）
  3. requires 解析：对每个契约名 C
       a. 已有激活的提供者 → 继续
       b. 没有 → 在**全部已登记插件**的 provides 里找提供者（可以还没激活）
              · 找到多个：按登记顺序依次尝试激活，第一个成功提供 C 的即为提供者
              · 一个都没有：P 置 Failed，原因 = "缺少契约提供者 C"
              · 提供者激活失败：P 置 Failed，原因 = "契约提供者 X 激活失败"
       c. 懒激活在这里发生：requires 是"隐式触发点"，插件不需要也不应该自己触发别人的激活
  4. conflicts 检查（若声明）：命中 → P 置 Failed（后激活的一方失败，已激活的一方不动）
  5. 循环检测：依赖闭包里出现自己 → 闭包内全部 Failed，原因 = "循环依赖 A→B→A"
  6. 构造上下文 → 初始化 P（§4.2 第 4 步起）
```

#### 5.6.3 停用时的反向级联（客户端自动做）

停用插件 X 时，**MUST** 自动处理依赖它的插件（否则会留下"能用但提供者已经没了"的僵尸插件）：

```
Deactivate(X):
  1. 计算反向闭包：所有 depends 里含 X 的插件，以及所有 requires 的提供者**只剩 X** 的插件
  2. 按逆拓扑顺序（依赖者先停）逐个停用，并记日志"因 X 停用而级联停用"
  3. 再停用 X 本身（§4.2 的收尾顺序）
```

- 级联停用**MUST** 是幂等的：重复停用不报错、不重复触发贡献撤下。
- `essential` 插件被请求停用 → **MUST** 拒绝（用户禁用清单里不允许出现它）。
- 如果被级联停用的插件是 `essential` → 拒绝停用 X 本身，并给出"X 被必需插件依赖"的原因。

#### 5.6.4 失败传播

- 提供者失败 → 所有 `requires` 它的插件在激活时自动 Failed（不需要真被调用）。
- 依赖插件失败 → 依赖者在激活时 Failed。
- 失败**MUST** 可读：错误信息要含"缺什么 / 谁失败 / 当前状态"，便于插件页展示与用户排查。
- 失败**MUST NOT** 抛到宿主启动流程外（§4.5）。

#### 5.6.5 插件不许做的事

- **MUST NOT** 自己反射/遍历注册表去找"某个具体插件的实例"。
- **MUST NOT** 在自己代码里写死 `new 某实现()` 来绕过契约（那是把实现焊死）。
- **MUST NOT** 在 `requires` 之外偷偷 `Get` 未声明的契约（有些实现会因此直接报错，属于预期行为）。
- **MUST NOT** 依赖"某个插件一定已激活"而省略声明——顺序由内核决定，不由插件假设。

## 6. 事件总线

- 订阅返回**可释放句柄**；上下文**MUST**代管订阅（停用时自动断开，插件忘记 Dispose 也不泄漏）。
- 分发**默认同步**（内核内的事件都很快）；**单个订阅者抛异常 MUST NOT 影响其他订阅者**，
  异常要被捕获、记日志、继续分发。
- 事件是"**事实广播**"，载荷**MUST**是不可变值（record/结构），**MUST NOT** 携带可变的宿主对象引用。
- 事件**MUST NOT** 被用来替代请求-响应（那是契约的职责）。
- 事件类型属于**发布方**（`PluginActivated` 属于内核，`VersionInstalled` 属于版本插件）。

## 7. 插件上下文（PluginContext）

插件能拿到的一切都从这里来，**MUST NOT** 使用全局单例（否则卸载残留、多实例冲突）。

| 成员 | 语义 | 跨平台注意 |
|---|---|---|
| `descriptor` | 本插件描述符（只读） | — |
| `kernel` | 内核门面：`Get/GetAll/TryGet/ProviderOf` | 解析**不阻塞**（§4.4） |
| `services` | 注册实现（仅激活期可写） | 线程安全 |
| `events` | 订阅（自动代管）/广播 | 同步分发 |
| `contributions` | 挂 UI 贡献点（§8） | 只登记，不直接碰视图 |
| `settings` | 本插件配置分区（键值，改一次存一次） | 见 §10 |
| `log` | `info/warn/error`（带插件 id 前缀） | 必须走宿主日志系统 |
| `paths` | `data`（持久）/ `cache`（可清理） | 由宿主按平台给（§11.1） |
| `permissions` | 本插件被授予的权限 | 只读 |
| `scheduler` | **宿主注入的调度器**：`post(task)`、`delay(ms, task)`、`spawn_background(task)` | 插件**MUST NOT** 自己起线程/定时器（§11.3） |
| `subscribe<T>(handler)` | 订阅并自动代管 | — |

上下文是**一次性**的：停用后不得再用（用即抛/记错误）；重新启用会拿到**新的上下文实例**。

## 8. UI 贡献点

### 8.1 机制（引擎级，宿主无关）

- 宿主提供**挂载位（slot）**：每个挂载位有 `id`、可接受的贡献种类、排序规则。
- 插件**声明**贡献，宿主/引擎负责渲染；插件**MUST NOT** 直接操作视图树。
- 增删**MUST** 在运行期生效且不重建整窗；**MUST** 支持 priority 排序与"查询某挂载位现有内容"。
- 卸载插件**MUST** 撤下其全部贡献，且**MUST** 释放对应视图（含 GPU 资源与事件订阅）。

### 8.2 贡献种类（本规范定义的最小集）

| 种类 | 字段 | 宿主落点（示例） |
|---|---|---|
| `navItem` | `id, title, glyph, pageId, order, footer` | 主导航 / 子导航 |
| `page` | `id, title, factory` | 页面宿主（**懒创建**：点开才建） |
| `homeCard` | `id, title, view, order` | 首页卡片区 |
| `section` | `id, target, title, view, order` | 设置页 / 详情页的分区 |
| `slot` | `id, target, view, order` | 页面内插槽 |
| `overlay` | `id, view` | 浮层/对话框 |

- `id` 在**同一插件内唯一**；重复挂同 id = 先撤旧再挂新（支持热重载）。
- `page` 的 `factory` **MUST** 是惰性的（不在登记时创建）；页面关闭 **MUST** 能释放。
- 视图**MUST** 由"声明式描述"或"宿主视图工厂"二者之一表达，**MUST NOT** 是引擎私有对象。

### 8.3 跨软件通用性

- 引擎/宿主**MUST NOT** 把"启动器语义"写进挂载位（不要有 `versionSections` 这种硬编码类型）；
  具体挂载位清单属于宿主，插件按宿主文档填 `target`。
- 同一份规范要能表达"工具类软件的侧栏面板""编辑器的编辑器区/状态栏"等形态（用 `slot` + `target` 覆盖）。

## 9. 权限与信任边界

| 信任等级 | 运行形态 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **内置内置** | 进程内，宿主编译期/同程序集 | 全部宿主 API + 全部契约 | 无（但**必须**登记权限用于审计） |
| **外部插件** | 沙箱（脚本运行时 / 子进程） | 仅 manifest 声明的权限命名空间 | 直接调宿主 API、动态加载原生库、访问未授权路径 |

权限语法与风险分级**沿用 v2 §5**（`net.http`、`fs.read:<scope>`、`fs.write:<scope>`、`ui.notify`、
`game.launch`、`ai.llm` 等；有风险的操作**MUST** 运行期二次确认）。
新增要求：

- **MUST** 在加载前校验：权限未声明却被调用 → 拒绝并记审计日志（不要静默失败）。
- **MUST** 支持"可选权限"（`optionalPermissions`）：首次用到时向用户申请。
- 外部插件**MUST NOT** 参与"契约实现"的注册（除非宿主显式支持跨边界契约，见 §15 决策项）。
- 卸载外部插件**MUST** 撤销全部权限与代管资源。

## 10. 数据与配置

- 每个插件**MUST** 有独立配置分区（键值 JSON），路径见 §11.1，**MUST NOT** 读写其它插件的分区。
- 配置写入**MUST** 原子（先写临时文件再 rename），**MUST** 容忍损坏（读失败按默认值，不崩溃）。
- 数据目录**MUST** 按插件 id 隔离；缓存目录**MUST** 可被安全清空。
- 插件**MUST NOT** 把配置写进程序安装目录（Linux 只读包、macOS bundle 只读）。
- 迁移：插件可自行在 data 目录里放版本号，做自己的迁移；内核不介入。

## 11. 跨平台规范（Linux / macOS / 六端）

### 11.1 路径（**MUST**）

内核不猜路径，由宿主注入三个根：`config`（配置）、`data`（持久数据）、`cache`（可清理）。
推荐映射：

| 平台 | config | data | cache |
|---|---|---|---|
| Windows | `%APPDATA%\<产品>` | 同 config（兼容既有布局） | `%LOCALAPPDATA%\<产品>\cache` |
| Linux | `$XDG_CONFIG_HOME/<产品>`（缺省 `~/.config/<产品>`） | `$XDG_DATA_HOME/<产品>`（缺省 `~/.local/share/<产品>`） | `$XDG_CACHE_HOME/<产品>`（缺省 `~/.cache/<产品>`） |
| macOS | `~/Library/Application Support/<产品>` | 同 config | `~/Library/Caches/<产品>` |
| Android / 鸿蒙 | 应用私有 filesDir | 同 config | 应用私有 cacheDir |

- 插件配置：`<config>/plugin-config/<id>.json`；插件数据：`<data>/plugin-data/<id>/`；
  缓存：`<cache>/plugin-cache/<id>/`。
- **大小写**：Linux 文件系统通常大小写敏感、macOS 默认不敏感 → 插件 id 与目录名**MUST**统一小写，
  比较**MUST**用序数（不做 locale 折叠）。
- 分隔符：manifest 内**MUST**用 `/`；内核在读入时归一化，写盘时用平台分隔符。
- **MUST NOT** 假设路径长度上限、**MUST NOT** 拼接未转义的用户输入。

### 11.2 编码与文本

- 所有文本（manifest、配置、日志、路径）**MUST** UTF-8（无 BOM）。
- 换行：源码/文本用 LF；`.cmd/.bat` 用 CRLF（仅 Windows）。
- 排序/大小写：**MUST** 用不变文化（invariant）比较；**MUST NOT** 用系统 locale 排序 id。
- 多语言：文案走宿主 i18n（§8 视图描述里用键，不写死中文）。

### 11.3 线程、事件循环、异步

- 内核**MUST NOT** 假设有 UI 线程或消息循环；宿主**MUST** 注入 `scheduler`（§7）：
  `post`（回到宿主主循环）、`delay`、`spawn_background`。
- 插件**MUST NOT** 直接创建线程/定时器（除宿主显式允许）；理由：六端的事件循环各不相同
  （Win32 消息循环、GLib、libdispatch/NSRunLoop、Android Looper、ArkUI 主线程），
  自行起线程会导致停用时无法收敛。
- 激活/停用**MUST** 可异步（返回 future/promise）；内核**MUST**等待其完成后再改变状态。
- 取消：所有可能长的操作**MUST** 接受取消令牌（`stop_token` / `CancellationToken` / 等价物），
  页面关闭时**MUST** 能取消后台取数。
- 线程安全：注册表、事件总线、贡献表**MUST** 线程安全；插件自己的状态由插件负责。

### 11.4 原生插件与 ABI

- **内置插件推荐编译期登记**（静态链接进宿主），**不引入 ABI 问题**：这是 Linux/macOS 首选。
- 若确实要动态加载原生插件（`.so` / `.dylib` / `.dll`）：
  - **MUST** 用 **C ABI** 导出（不导 C++ 对象/STL/exceptions/编译器私有布局）；
  - **MUST** 带 `abi_version` 与 `api_version`，加载前校验，不匹配拒绝；
  - **MUST** 支持"卸载失败也不崩"（能被标记为需重启生效）；
  - **MUST** 说明平台差异：macOS 需 hardened runtime + 公证/签名；Linux 无强制签名、需自行校验完整性。
- 外部脚本插件（JS/Python）**MUST** 走宿主提供的脚本运行时接口，内核不绑定具体引擎
  （C++ 可用 QuickJS/Duktape/Python 子进程；C# 侧参考实现用 Jint/Python 子进程）。

### 11.5 平台差异性（**MUST** 在宿主侧处理，不得泄漏进内核/插件契约）

| 事项 | Windows | Linux | macOS |
|---|---|---|---|
| 文件监听 | ReadDirectoryChangesW | inotify | FSEvents |
| 默认浏览器/文件管理器 | ShellExecute | xdg-open | NSWorkspace |
| 进程拉起 | CreateProcess | fork/exec | posix_spawn |
| 高 DPI | PerMonitorV2 | X11/Wayland scale | Retina backing scale |
| 毛玻璃/材质 | DWM Acrylic/Mica | 无原生（自绘） | NSVisualEffectView |
| 快捷键全局捕获 | RegisterHotKey | X11 grabs / Wayland 受限 | 辅助功能授权 |
| 代码签名 | Authenticode | 无（可选） | 公证 + hardened runtime |

插件**MUST** 通过宿主的"宿主装配接口"使用这些能力（见 §15 与引擎需求 N4），不得自己直连。

## 12. 端口落地骨架（参考形状，非强制）

```
<port>/
  kernel/            内核：event_bus / service_registry / plugin_host /
                     contribution_registry / descriptor / context
  contracts/         宿主契约定义（IDownloadEngine、IVersionCatalog …）
  plugins/builtin/   内置插件（编译期登记）
  plugins/external/  外部插件宿主（沙箱、运行时、权限）
  shell/             窗口、导航、页面宿主、浮层、主题、i18n、动效档位
```

最小接口形状（C++ 伪代码，**MUST** 语义一致，命名可本地化）：

```cpp
class plugin {
public:
  virtual ~plugin() = default;
  virtual nebula::future<void> initialize(plugin_context& ctx) = 0;
  virtual nebula::future<void> shutdown() = 0;
};

class service_registry {
public:
  virtual void add(std::type_index contract, std::shared_ptr<void> impl, int priority) = 0;
  virtual std::shared_ptr<void> get(std::type_index contract) = 0;       // 同优先级后注册者胜
  virtual std::vector<std::shared_ptr<void>> get_all(std::type_index) = 0;
  virtual void remove_by_provider(std::string_view plugin_id) = 0;
};

class kernel {
public:
  virtual void register_plugin(plugin_descriptor, plugin_factory) = 0;   // 动态登记（外部插件用）
  virtual nebula::future<void> start() = 0;
  virtual nebula::future<bool> activate(std::string_view id) = 0;        // 含依赖递归 + 环保护
  virtual nebula::future<void> deactivate(std::string_view id) = 0;
  virtual service_registry& services() = 0;
  virtual event_bus& events() = 0;
  virtual contribution_registry& contributions() = 0;
};
```

要点：`register_plugin` 允许**运行期**登记（外部插件在启动后加载），不是只在启动时登记。

## 13. 验收清单（端口实现逐项打勾，**每项都要有自动化用例**）

**描述符与登记**
- [ ] 重复 id 登记 → 拒绝并报错（不覆盖）
- [ ] `apiVersion` 主版本不一致 → 拒绝加载，错误信息含双方版本
- [ ] manifest 含绝对路径 / 反斜杠 → 拒绝或归一化后告警
- [ ] 插件 id 非小写 → 拒绝（跨平台大小写一致）

**契约**
- [ ] 同契约多实现：取优先级最高者
- [ ] 同优先级：**后注册者胜**；停用它后回到次高
- [ ] `GetAll` 按优先级降序返回
- [ ] 用具体类注册 → 抛错（"契约必须是接口"）
- [ ] 停用插件 → 其全部登记消失，`Get` 抛"没有提供者"
- [ ] 注册表并发注册/解析无崩溃（压测 2 线程 × 1000 次）

**生命周期**
- [ ] 激活次序：engine → feature → assistant → ui
- [ ] 依赖先于被依赖者激活
- [ ] **循环依赖 A→B→A：不死循环、不栈溢出，双方 Failed 且有可读原因**
- [ ] 依赖缺失 → Failed（"缺少依赖 X"），宿主启动不受影响
- [ ] 懒插件：启动后为 Registered；首次 `Get` 后变 Active
- [ ] 懒插件在 UI 线程上被请求时不阻塞（返回 future 或立即失败）
- [ ] 停用 → 再启用：状态、贡献数、订阅数回到基线（不允许翻倍）
- [ ] 激活中抛异常 → Failed + 错误信息，不冒泡到宿主

**依赖自动处理（§5.6，**每一项都要有独立用例**）**
- [ ] `requires` 的提供者未激活 → 激活插件时**自动激活提供者**（隐式懒激活），插件正常起来
- [ ] `requires` 的提供者一个都没有 → 插件 Failed，原因含缺失的契约名
- [ ] `requires` 有多个提供者 → 按登记顺序取第一个成功提供者；停掉它后再次激活能换到下一个
- [ ] `depends` 版本范围不满足 → Failed（不降级、不"凑合用"）
- [ ] `depends` 的插件不存在 → Failed，原因可读
- [ ] 依赖链 A→B→C：激活 A 时 B、C 按序激活；停用 C 时 A、B **按逆拓扑自动级联停用**
- [ ] `requires` 的提供者被停用 → 依赖它的插件**自动级联停用**（不留僵尸插件）
- [ ] 级联停用幂等：重复调用不报错、不重复撤贡献
- [ ] `essential` 插件：禁止用户停用；被必需插件依赖的插件也禁止停用（给出原因）
- [ ] `conflicts` 命中 → 后激活者 Failed，先激活者不受影响
- [ ] 循环依赖 A→B→A（含 requires 与 depends 混合成环）→ 闭包内全部 Failed，**进程不崩**
- [ ] 插件的 `Get` 未在 `requires` 里声明的契约 → 按实现策略拒绝或告警（不允许静默通过）

**事件**
- [ ] 退订后不再收到
- [ ] 一个订阅者抛异常，其它订阅者照常收到
- [ ] 停用插件后其订阅数归零（含忘记 Dispose 的情况）
- [ ] 广播载荷不可变（review 项）

**贡献点**
- [ ] 运行期增删贡献不重建整窗
- [ ] 同 id 重复挂 → 旧撤新挂
- [ ] priority 排序生效
- [ ] 停用 → 贡献清零、视图释放（GPU 资源与订阅一并释放）
- [ ] 页面懒创建：注册后不创建，首次进入才创建
- [ ] 单插件视图抛异常 → 该贡献降级为占位并上报，其它界面正常

**权限 / 数据**
- [ ] 未声明权限被调用 → 拒绝 + 审计日志
- [ ] 可选权限首次使用时向用户申请
- [ ] 插件 A 无法读插件 B 的配置分区
- [ ] 配置写入原子；配置文件损坏时按默认值启动
- [ ] 安装目录（Linux 包/macOS bundle）保持只读，不写任何文件

**跨平台**
- [ ] config/data/cache 三根按 §11.1 落到正确位置；XDG 变量被尊重
- [ ] 插件在大小写敏感文件系统（Linux ext4）与不敏感（macOS APFS 默认）行为一致
- [ ] 插件不自行起线程/定时器（代码扫描 + review）
- [ ] 取消令牌贯穿所有长操作；页面关闭后无回调打到已释放视图
- [ ] 原生插件（若启用）ABI/API 版本校验生效；不匹配拒绝加载

## 14. 已知坑（照这些避）

1. **循环依赖栈溢出**（参考实现踩过）：激活状态必须在递归依赖**之前**置位。否则 A→B→A 会无限递归，
   直接把进程打崩（不是抛异常，是整个宿主挂掉）。
2. **"契约必须是接口"会打脸迁移期**：老服务按具体类互相构造，如果把它登记成契约会触发校验失败 →
   插件激活失败 → 宿主同步取服务 → 启动失败。迁移期用 §5.4 的过渡口子，或一步到位重构成契约。
3. **同优先级"后注册者胜"**：写反了会变成"先注册者胜"，导致新插件永远覆盖不了内置实现。
4. **激活耗时不是免费**：同步启动内核时，任何带 I/O 的 `eager` 插件都会拖慢启动；
   参考实现里投影解析占 2.5~3.3 秒，就是该改成 `lazy` 的典型。
5. **卸载泄漏**：视图、事件订阅、定时器、文件句柄必须被内核代管；只靠插件自觉一定会漏。
6. **订阅代管**：插件直接 `events.Subscribe` 而忘记 Dispose → 停用后仍被回调 → 访问已释放对象。
   上下文必须提供"自动代管订阅"的入口，并测试"忘记 Dispose 也不泄漏"。
7. **事件载荷别传宿主对象**：传了就是把宿主的生命周期塞给插件，必然泄漏。
8. **UI 线程假设**：不要假设"激活发生在主线程"，也不要假设"有主线程"；一切经调度器。

## 15. 与 UI 框架（Nebula）的边界 + 需要框架提供的能力

**边界（**MUST**）**：

- 插件模型（描述符、生命周期、契约、权限、沙箱）= **宿主领域**，各软件各一套实现；
  UI 框架**MUST NOT** 内置业务契约或插件系统本体。
- 视图树构建、挂载位、令牌、动效、渲染 = **框架职责**；框架**MUST NOT** 知道"启动器"是什么。
- 框架与内核之间只有两个接触面：**视图工厂/声明式视图**、**贡献点挂载位**。

**框架必须提供（详见 `docs/designs/2026-10-15-nebula-engine-requirements.md`）**：

| 编号 | 能力 | 优先级 |
|---|---|---|
| N1 | 运行时构建视图树（声明式 + 命令式，同一棵树） | P0 |
| N2 | 页面/贡献点动态增删 + 懒创建 + 真释放 | P0 |
| N3 | 宿主注入服务解析器（插件不碰单例） | P0 |
| N4 | 宿主装配接口（窗口/文件选择/通知/进程拉起/网络代理…） | P1 |
| N5 | 错误隔离（单贡献失败不拖垮宿主） | P1 |
| N6 | 动效档位 + 无障碍降级 | P1 |
| N7 | 令牌只读访问 + 主题变更通知 | P2 |
| N8 | 多语言查询 + 切换通知 | P2 |
| N9 | 异步与取消原语（六端一致） | P2 |
| N10 | 体素/皮肤模块宿主化（解析与交互可注入） | P3 |
| N11 | 装载时序与激活耗时上报 | P3 |

**需要宿主（端口）自己决定的决策项**：

- 外部插件能否提供契约实现（跨沙箱边界的契约）？建议先只支持进程内形态（§9）。
- 动态加载原生插件是否启用？建议内置走编译期登记，动态加载只在确有需求时按 §11.4 做 C ABI。
- 必需插件（`essential`）清单：哪些插件不允许用户禁用（如设置/日志/下载引擎）。
- 沙箱实现选型（JS 引擎、Python 子进程），以及权限二次确认的 UI 形态。
