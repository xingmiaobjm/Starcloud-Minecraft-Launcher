# 关于近期针对 PCL 所谓「后门」指控的技术说明

> 状态：草稿，未发布
> 建议 id：`2026-10-24-pcl-backdoor`（客户端按 id 记已读，发布后不可复用旧 id 改内容）
> 置顶：是
> 落款：星云创新

近日，网络平台传播有关 PCL（Plain Craft Launcher）联网配置功能存在「后门」的言论。PCL 作者已于 2026 年 10 月 23 日发布《有关 PCL 存在所谓「后门 / 漏洞」的说明》。我们经核阅该说明及已公开的技术信息，现就有关事项说明如下。

## 一、关于所谓「漏洞」的成立条件

据披露方演示的复现流程，实施该攻击须以攻击者已掌握 PCL 的整个更新服务、已能篡改 HTTPS 传输内容，或已能篡改用户本机文件为前提。作者已就「CDN 内容被恶意篡改」列举三种可能，原文如下：

> 黑客已经黑入了你的网络，并且可以篡改 HTTPS 加密传输内容。
> 那为啥黑客不修改 PCL 更新包？
>
> 黑客已经黑入了 PCL 在腾讯云的 CDN。
> 那他已经无敌了，投了吧。
>
> 黑客已经黑入了你的电脑，并且可以篡改你的文件了。
> 既然黑客已经可以直接篡改文件了，为啥还要专门绕一个弯间接修改设置文件？直接改不好吗？

上述三种情形，均以攻击者已取得远强于该路径本身的控制能力为前提。在此前提下，攻击者本可直接修改更新包或直接修改本机文件，无须经由「联网配置 — 启动前执行命令」这一间接路径。该路径对攻击者不构成额外的利用能力。

同时，若以「可信服务向客户端推送信息」本身作为漏洞成立的前提，则任何软件均可被同一方法「复现」为存在后门，该推论显然不能成立。

此外，PCL 默认不以管理员权限运行，提权操作亦不触发联网配置执行代码，不存在借此提升权限的可能。

## 二、关于该功能的正当用途

联网配置属程序更新机制的组成部分，其设置项与公告、更新弹窗同源，用途在于应急止损：其一，老版本出现安全漏洞而用户已关闭自动更新的情形下，可远程关闭存在漏洞的功能模块，降低影响；其二，第三方服务异常致启动器开启后数秒内反复崩溃、用户无从进入设置的情形下，可在崩溃前调整配置，避免死循环。据作者说明，涉及设置修改的路径迄今未被实际使用。

## 三、关于开发者动机的推定

具备某项能力，不等于将予实施。作者就此指出：「有操作的能力不等于要进行操作。这个逻辑就是，龙猫买了把菜刀 = 龙猫在偷偷准备用菜刀杀人……」。就技术层面而言，任何程序本可修改其新版本更新包以实现所谓「远程下发恶意代码」，并无设计迂回结构之必要。

## 四、关于披露方式与作者所处的处境

据作者说明，其从未收到相关问题的 Issue 或 Security Advisory；而 PCL 此前已通过 GitHub Security Advisory 渠道安全处理 4 项安全漏洞。作者就披露方式指出，「对于任何可能的安全漏洞，绕过作者直接发布都是极度不负责的行为」。

我们还注意到以下事实：作者称其 GitHub 账号均已被封禁，无法通过 GitHub 发布说明，只能发布于 B 站；发文时，PCL 相关 CDN 正遭受 DDoS 攻击而处于瘫痪状态；作者亦表示，未告知或授权任何人在视频中使用其真实姓名。

一位独立开发者，在账号被封、服务被攻击的情况下，只能在自己的动态里逐条回应一份公开指控。无论技术判断如何，这已不是一次正常的漏洞披露应有的样子。

## 五、关于我们自己的情况

同类指控若落到我们自己头上，最直接的检验方法是：远程服务究竟能不能改写敏感设置，以及更新链路能不能被单个文件篡改。就此，我们将 SCML 的情况一并说明，供对照：

- 云端公告通道为只读，客户端仅将其渲染为纯文本，不解析 HTML、不加载远程资源、不执行脚本，链接仅放行 http/https 并交系统浏览器打开；该通道唯一会写入本地的是「已读公告 ID」。
- 自更新清单仅包含版本号、更新说明与产物的文件名、SHA256、大小，**不包含任何设置项或命令字段**，客户端不会依据该清单改写本地配置。
- 更新清单采用 ECDSA P-256 签名校验，公钥编译于客户端内，验签失败即拒绝本次更新；更新产物须通过 SHA256 与文件大小双重校验，字段缺失或格式非法一律拒绝，不作降级处理。
- 更新清单与产物的地址均强制使用 HTTPS。
- Java 路径、JVM 参数、下载源、启动前/后命令等敏感设置，只接受本地界面输入并保存于本机配置文件，不接受远程下发。

换言之，即使服务端全部失守，攻击者也无法借此获得改写上述设置的能力，亦无法借一份被篡改的清单推送任意程序。这一结论是可核查的，欢迎任何人核查。

## 结语

本说明基于已公开信息作出，仅就技术事实与披露程序进行陈述，不构成对任何一方的主观评价，亦不替代专业安全机构的独立评估。

我们主张：发现问题的能力值得尊重，但披露的方式同样应当审慎；在证据缺位时，一款持续维护多年的软件不应被「后门」二字轻易定性。
