# 玩家形象 GPU 硬件加速设计

日期：2026-09-20
状态：已实现
所属：PCL2 平替（账户页形象渲染）

## 1. 背景与问题

用户诉求：

> 添加 GPU 硬件加速的能力。

现状（软件光栅化，见 [皮肤查看器设计](2026-09-12-skin-viewer-design.md) §3.4）：

1. **一帧几十毫秒**。这台机器实测 630×1020 一帧 58ms（约 17fps），
   而走路动画需要 30fps 才顺。
2. **代价是清晰度**。撑不住时 `SkinFigureView` 走"自适应降档"（最低 0.85 倍）
   并用线性放大，像素风的边会糊掉——这正是用户当初反馈"锯齿/糊"的另一面。
3. **算力全在 CPU 上**，和启动器自身的 UI、下载、解压抢同一批核心。

## 2. 目标与不变量

- 形状、姿势、相机、采样规则**与软件路径保持一致**：换 GPU 不该换来另一种画风。
- 没有可用的显卡 / 驱动 / `d3dcompiler_47.dll`（或非 Windows）时**必须能退回软件路径**，
  不能因为加了个"加速"反而让用户看不到形象。
- 不引入跨设备共享纹理、不把设备暴露给 Win2D、不新增线程时序问题。

## 3. 方案

### 3.1 新增 `SkinGpuRenderer`（`Starcloud.Core/Rendering/`）

基于 D3D11 的硬件光栅化（Vortice 托管封装，纯 P/Invoke，无原生运行时依赖）：

```csharp
public sealed class SkinGpuRenderer : IDisposable
{
    public static SkinGpuRenderer? TryCreate(bool allowSoftwareDevice = false);  // 失败返回 null
    public string DriverName { get; }
    public BitmapFrame Render(SkinModel skin, RenderOptions opts, int width, int height, Pose? pose = null);
}
```

管线：顶点缓冲（每面 2 个三角形）→ 顶点着色器（屏幕像素 → NDC）→ 逐像素 Z 测试
→ 像素着色器（`Texture2D.Load` 取纹素并按面片矩形钳制）→ 预乘 alpha 混合。

关键点：

- **不做背面剔除**、**不开 MSAA**、**不引采样器**（`Load` 就是最近邻整数取数），
  与 CPU 的 `(int)u` 取数、硬边像素风完全对齐。
- **深度**：`D32_Float`，`Less`（相等时先画的先占位，与 CPU 的 `iz <= depth 则跳过` 一致）。
- **透视校正**：顶点着色器输出 `w = 1`（自己在 CPU 侧做完除法），
  于是硬件只做屏幕空间线性插值；片元里再按 `(uv/z) / (1/z)` 补回透视除法——
  与 CPU 的逐像素公式**同构**。若省掉这步，旋转视角下纹素归属会整体偏出约 1 像素
  （实测表现为每个纹素边界都错开一格）。
- **采样边界**：和软件路径同样把纹素坐标钳在本面片 UV 矩形内
  （`Right-1` / `Bottom-1`）。这是"模型边缘杂色描边 / 虚线"那个 bug 的根因，
  两条路径都必须遵守。

### 3.2 投影只有一份实现

新增 `SkinProjection`（`Rendering/SkinProjection.cs`）：模型 → 屏幕坐标 + 相机深度 + 纹素 UV，
返回按"由远到近"排序的可见面片。`SkinRenderer` 与 `SkinGpuRenderer` 都吃这份结果，
差别只在"谁来光栅化"。原先把这段数学埋在软件光栅化器内部，加 GPU 路径时若照抄一份，
两条路会慢慢跑偏。

顺带修掉一个浪费：软件路径原本**每条扫描带都重新投影一遍所有面片**，现在只投影一次。

### 3.3 取帧方式：GPU 渲染 → 回读 → 交给现有 Win2D 位图

```
后台线程：模型/投影 → D3D11 光栅化 → CopyResource 到 staging → Map 回读 BGRA
UI 线程：  CanvasBitmap.SetPixelBytes(那一帧) → 画布重绘
```

**为什么不直接共享纹理（零拷贝）**：那样必须让 Win2D 用我们创建的 D3D11 设备
（`CanvasDevice.CreateFromDirect3D11Device` + `CanvasControl.CustomDevice`），
于是同一份 D3D11 立即上下文被两条线程（后台渲染 / UI 绘制）交替使用——
立即上下文不是线程安全的，而 Win2D 内部何时提交命令我们无法插手。
回读 2.6MB 约 1ms，换来"设备完全私有、线程模型与原实现一模一样"，
在启动器这种要长期稳定运行的程序里是划算的。

## 4. 实测

同一台机器（NVIDIA GeForce MX450），300×600：

| 项目 | 软件光栅化 | GPU 光栅化 |
| --- | --- | --- |
| 稳定帧耗时 | 50~80ms | **0.8~2.1ms** |
| 首帧（建设备 + 编着色器） | — | 30~55ms（仅一次，后台线程） |

## 5. 一致性验证（`SkinGpuTests`）

GPU 路径的验收标准不是"能出图"，而是"和软件路径同图"：

1. **结构一致**：轮廓归属不同的像素 ≤ 8%（三条尺寸 × 四个视角实测 ≤ 3.6%）；
   "干净像素"（两张图里都不是 1 像素边）里大差 ≤ 3%（实测 ≤ 1.2%）；
   干净像素占比 < 20% 时判据本身失效，直接失败。
2. **已知允许的差异**：CPU 的保守填充（三角形外半像素也着色）让轮廓与面片接缝
   比真实几何宽 ≤1px，GPU 用硬件的精确填充规则，所以那一圈像素归属天然不同；
   另外少数像素正好压在纹素边界上，float（CPU）与定点（硬件）插值会取到相邻纹素。
   颜色整体错位（例如 BGRA 弄反）、丢面、几何错位都会让判据爆表——开发过程中
   R/B 反、仿射插值这两个 bug 都是这条用例抓出来的。
3. **边界与不变式**：边缘不采面片 UV 之外的纹素（洋红陷阱皮肤）；输出为不超过 alpha 的预乘 BGRA；
   换尺寸（200×400 → 320×480 → 回 200×400）后仍与软件一致（渲染目标/深度/staging 都是按尺寸缓存的）。
4. **HLSL 必须纯 ASCII**：Vortice 把源码按 ANSI 交给 D3DCompile，源码里的中文注释会被截断成
   `X3000: unexpected end of file`。这条约束用一条专门用例钉住。

环境不支持 D3D11（含 WARP）时用例跳过——本项目只跑在 Windows 上，WARP 兜底后基本不会发生。

## 6. 回退与日志

- `SkinFigureView` 首次渲染时在**后台线程**尝试建 GPU 渲染器（约 30~50ms，不卡 UI）。
- 建不起来或渲染抛异常（设备丢失、驱动更新）→ 永久回退软件路径，并补一帧，
  日志：`player3d GPU 渲染器不可用，回退软件光栅化：<原因>`。
- 启用成功时日志：`player3d 皮肤预览启用 GPU 硬件加速（<显卡名>）`。
- 走 GPU 时禁用自适应降档（固定 1:1）；软件路径保留原有降档逻辑。

## 7. 风险与后续

1. **首帧 30~50ms**：发生在后台线程，用户感知为"形象晚出现半帧"，可接受。
2. **多一个依赖**：Vortice 系列 4 个包进 Core（此前 Core 只有 Jint）。
   只在 Windows 上真正建 D3D11 设备，其余平台直接返回 null。
3. **回读仍是 CPU 往返**：下一步若要再压，可换 `SwapChainPanel` + 自有交换链
   （`ISwapChainPanelNative` 互操作已在 `Views/SwapChainPanelNative.cs` 备好），
   彻底省掉回读与 Win2D 上传；代价是渲染线程模型要重做。
4. **软件路径不再是最快路径**：它保留为兜底与单元测试参照实现，不再为它做性能优化。
