# 内核与插件化总设计：万物皆插件

> 2026-10-15。目标：把启动器本体退化成"**内核（Kernel）+ 外壳（Shell）**"，
> 一切功能——Nova、Nova 执行器、多线程下载引擎、版本管理、存档、联机、SC 实验室……
> 全部以**插件**形式挂上去。插件分两级信任：**内置插件**（进程内、完全信任）和
> **第三方插件**（沙箱、权限白名单），但**共用同一份契约与同一套 UI 贡献机制**——
> 内置插件只是"信任等级最高的插件"。
>
> §8 是给 Nebula / starcloud-ui 框架的需求清单，可直接转给做框架的 agent。
> **框架是跨软件通用引擎**（不止启动器，后续还有别的软件），所以 §8 的需求一律写成
> "引擎级能力"，不出现启动器、Nova、投影这类专有名词；启动器只是它的第一个宿主。

---

## 1. 为什么要做

现状（本仓库）：`Starcloud.Core` 有 **79 个服务文件**，`AppServices` 是手工接线的单例容器，
15 个页面直接吃 `AppServices.Instance.*`。后果：

- **换不掉**：下载引擎、投影解析、LLM 网关都写死在容器里，想换实现要改一堆调用点。
- **关不掉**：不用联机/不用 Nova 的用户也得背着这些代码与初始化开销。
- **装不动**：已经有一套很强的外部插件系统（`docs/plugin-spec-v2.md`：manifest、权限、
  依赖解析、声明式 UI、导航项/卡片/分区贡献点 ✅），但**内置功能接不进这套机制**，
  于是"插件能做的事"永远比"本体能做的事"少一档。
- **跨界难**：本项目正在用自研 Nebula 引擎重做六端（`starcloud-ui`），
  内核/插件的契约必须是**语言无关**的（C# 与 C++ 各实现一份），单例容器没有这种边界。

插件化之后：每个功能都能被替换、被禁用、被懒加载，第三方可以写一个下载引擎插件把内置的换掉。

**不变量（做这个重构的底线）**：

1. 任何一步都必须**可运行、测试全绿**（绞杀者模式，不允许大爆炸式重写）。
2. 用户可见行为不变（除非那一步本身就是要改行为）。
3. 内核不依赖任何具体功能：内核里出现 `Download`、`Nova`、`Version` 这些词就是设计错误。
4. 契约是**语言无关的规格**：C# 与 Nebula（C++）各实现一份，插件不许依赖宿主语言类型。

## 2. 分层

```
┌─ 外壳 Shell（内核的一部分，但不是功能）─────────────────────────┐
│  导航（主导航/子导航，动态）· 页面宿主 · 浮层与通知 · 主题与材质令牌   │
│  任务中心面板 · 设置框架 · 多语言 · 动效档位                        │
├─ 内核 Kernel（最小）───────────────────────────────────────────┤
│  设置与路径 · 日志 · 事件总线 · 服务注册表 · 插件宿主               │
│  （装载 / 依赖解析 / 生命周期 / 权限裁决 / 贡献点注册表）            │
└───────────────────────────────────────────────────────────────┘
        ▲ 插件通过 ctx 拿到内核；插件之间只通过「契约 + 事件」通信
┌─ 插件（内置 = 进程内完全信任；外部 = 沙箱 + 权限）──────────────────┐
│ 引擎类：下载引擎 · 投影渲染 · 皮肤渲染 · LLM 网关 · 联机链路 · 资源源  │
│ 功能类：版本/实例 · 存档库 · 账户 · Java · 整合包导入 · 诊断          │
│ 助手类：Nova 对话 · Nova 执行器 · 各 Nova 工具 · 指令助手             │
│ UI 类：页面 · 首页卡片 · 设置分区 · 版本页分区 · 状态栏胶囊 · 浮层     │
└───────────────────────────────────────────────────────────────┘
```

**一句话判据**：内核是"没有它插件跑不起来"的东西；只要有插件可以不做它，它就该是插件。

### 2.1 与框架（Nebula）的关系

插件化是**宿主（启动器）这一侧**的事；框架（Nebula / starcloud-ui）是**跨软件通用引擎**，
启动器只是它的第一个宿主。分工：

- 内核/插件/契约/权限 = 宿主领域（各软件各有一套，不进引擎）
- 视图树构建、动态挂载点、令牌、动效、渲染 = 引擎职责，**不认识"启动器"**
- 一份宿主的需求清单（启动器要什么引擎能力）在 §8，写成引擎级形态

换句话说：** Nebula 提供"能长出插件的骨架"，内核提供"插件怎么协作的规矩"。**

## 3. 插件模型

### 3.1 内置插件与外部插件的关系

| | 内置插件 | 外部插件 |
|---|---|---|
| 信任 | 完全信任（进程内，可直接调宿主 API） | 权限白名单 + 沙箱（Jint / 子进程） |
| 语言 | C#（Nebula 侧为 C++） | JS / Python |
| 目录 | 编译期内嵌（注册表，不扫盘） | `%APPDATA%/starcloud-launcher/plugins/<id>/` |
| manifest | 同一份 JSON 形状（编译期写死在代码里或随程序集附 JSON） | `manifest.json` |
| UI 贡献 | **同一套**（`contributes`） | **同一套**（`contributes`） |
| 能力 | 全量契约 | 受权限约束的宿主 API 子集 |

**关键收益**：外部插件能做的 UI 贡献，内置插件也走同一条路；反过来，内置插件提供的
**契约实现**可以被外部插件替换（例如"用我的下载引擎"），只需在设置里选实现。

### 3.2 manifest（内置插件用同一份字段，见 `docs/plugin-spec-v2.md` §3）

```jsonc
{
  "id": "starcloud.download",
  "name": "多线程下载引擎",
  "version": "1.0.0",
  "apiVersion": "3.0",
  "kind": "engine",              // engine | feature | assistant | ui
  "builtin": true,               // 内置插件标记
  "provides": ["IDownloadEngine"],   // 本插件对外提供的契约
  "depends": { "starcloud.settings": "^1.0.0" },
  "contributes": { "settingsSections": [{ "id": "download", "title": "下载" }] },
  "permissions": ["net.http", "fs.write:launcher"],
  "activation": "eager"          // eager（启动即激活）| lazy（被用到才激活）
}
```

### 3.3 生命周期

```
Discover（内置注册表 + 磁盘扫描合并）
  → Resolve（依赖拓扑排序，冲突检测，缺失依赖标记为不可用）
  → Activate（await InitializeAsync(ctx)：注册契约实现 + 挂 UI 贡献）
  → Running（处理事件、服务调用）
  → Deactivate（await ShutdownAsync()：撤下贡献、释放资源、注销契约）
```

- 激活顺序按 `kind` 分层：内核 → 引擎 → 功能 → 助手 → UI（引擎先于依赖它的功能）。
- `activation: lazy` 的插件在第一次 `Resolve<T>()` 命中它的 `provides` 时激活。
- 卸载必须是**可逆**的：贡献点全撤、事件订阅全断、契约注销；否则重启用会重复注册。

## 4. 契约清单（把现有 79 个服务归类）

契约命名 `I<职责>`，**按"能力"切，不按"类"切**——判据是"能不能被换实现"。
下表是启动器这一份宿主用到的契约（**这份表属于宿主，不属于框架**；框架只提供"按能力取用"的机制，
见 §8.4/§8.5）。已加粗的是 P0/P1 要先做的。

**通用能力**（其它软件的主机也会需要同名的，将来可上升为跨宿主契约）：

| 契约 | 能力 | 启动器现有实现 |
|---|---|---|
| **`IDownloadEngine`** | 文件/批量下载（并发、多源、进度、重试、校验） | `DownloadService` + `ChunkedFileDownloader` + `DownloadSource` + `ParallelGovernor` |
| **`IHttpGateway`** | 取文本 / POST JSON（所有联网能力的底座） | `DownloadService` 的 `GetStringAsync` / `PostJsonAsync` |
| `IIconCache` | 远程图片落地与复用 | `IconCacheService` |
| `ITranslationEngine` | 文本翻译 | `SearchTranslationService` |
| `ILlmGateway` | LLM 端点（流式、多套配置） | `LlmEndpoint` + `OpenAiSseClient` |
| `IPeerLink` | 设备间链路（发现、同步、复用） | `DeviceLink/*` |
| `IPluginStore` | 插件/组件的获取与安装（应用商店式） | `CurseForgeService` + `ModrinthService` 的包管理部分 |
| `ITaskScheduler` | 长任务登记与进度聚合 | `TaskCenterService` |
| `INotificationSink` | 通知 | `NotificationCenter` |
| `ICrashReporter` | 崩溃收集与分析 | `CrashAnalysisService` |

**领域契约**（启动器特有，可能只在这一份宿主里出现）：

| 契约 | 现有实现 |
|---|---|
| **`IVersionCatalog`** | `ManifestService` |
| `IInstanceManager` | `InstanceSettings` + `InstanceVersion` + `LauncherPaths` |
| `IGameLauncher` | `GameLauncher` + `GameSession` + `GameRunHistoryStore` |
| `ISaveLibrary` | `SaveService` + `SaveLibraryService` + `SaveSyncService` |
| `IAccountProvider` | `AccountStore` + `MicrosoftAuthService` + `YggdrasilService` + `LaunchAccountService` |
| `IJavaRuntimeProvider` | `JavaService` |
| `IModSource` | `ModrinthService` / `CurseForgeService`（多实现） |
| `IModPackInstaller` | `MrPackInstallerService` / `CurseForgePackInstaller` / `MultiMcPackService`（多实现） |
| **`IProjectionEngine`** | `Projection/*` + `Lab/*`（解析 / 几何导出 / 社区源） |
| `ISkinRenderer` | `SkinLibrary` + 皮肤渲染 |
| **`INovaAgent`** | `NovaService` + `NovaAgentLoop` |
| **`INovaTool`** | `NovaTools*`（读/写各一组）——**每个工具都是一个插件** |

> 通用契约在 Nebula 侧只需保证"引擎能按能力注入给插件"（§8.4），
> 契约定义本身留在各宿主代码里，不进引擎（§8.13）。

## 5. 内核 API（C# 侧的样子）

```csharp
// 事件总线：插件之间唯一的通信方式
kernel.Events.Publish(new VersionInstalled { Id = "26.3", Isolated = true });
kernel.Events.Subscribe<VersionInstalled>(e => { ... });

// 服务注册表：按契约注册/解析，支持多实现 + 优先级 + 显式覆盖
ctx.Services.Add<IDownloadEngine, ChunkedDownloadEngine>(priority: 100);
var engine = kernel.Services.Get<IDownloadEngine>();          // 取优先级最高的
foreach (var src in kernel.Services.GetAll<IModSource>()) ...  // 多实现

// 插件上下文：插件能看到的一切都从这里拿（不允许静态单例）
public interface IPluginContext
{
    IPluginInfo Info { get; }
    IKernel Kernel { get; }
    IServiceCollection Services { get; }        // 注册自己的实现
    IEventBus Events { get; }
    IContributionRegistry Contributions { get; } // 挂载 UI
    ISettingsScope Settings { get; }             // 插件自己的配置分区
    IPluginLogger Log { get; }
    IPluginPaths Paths { get; }
    IPluginPermissions Permissions { get; }       // 外部插件按 manifest 裁决
}
```

**纪律**：`AppServices` 从"服务容器"降级为"内核门面"——内部实现改成
`kernel.Services.Get<T>()`，页面与服务的调用点**一行都不用改**（这是迁移能小步走的关键）。

## 6. UI 贡献点

外壳按贡献点动态构建界面；插件卸载时撤回：

| 贡献点 | 宿主位置 | 现状 |
|---|---|---|
| `navItems` | 左侧主导航（含底部/子导航） | 外部插件已支持 ✅，内置页面改成同一机制 |
| `pages` | 页面宿主（按 id 创建，懒加载） | 新增（把 15 个硬编码页面搬过来） |
| `homeCards` | 首页卡片区 | 外部插件已支持 ✅ |
| `slots` | 页面内插槽（按 slot id） | 外部插件部分支持 ✅ |
| `versionSections` | 版本详情页分区 | 外部插件已支持 ✅ |
| `settingsSections` | 设置页分区 | 新增 |
| `overlays` / `statusPills` | 浮层 / 状态栏胶囊 | 新增 |

内置页面搬迁后，外壳不再硬编码 12 页；**启动时只装载被启用的插件**——
顺带治 `starcloud-ui` 那边"启动 6 秒、其中投影解析占 2.5~3.3 秒"的问题（投影插件改成 lazy）。

> 贡献点**机制**在框架侧要通用（引擎级挂载点，见 §8.3）；
> 上表这些具体名字（navItems/pages/homeCards/versionSections…）是**本宿主**的挂载位清单，
> 框架不需要知道它们叫什么，也不需要知道"版本详情页"是什么。

## 7. 迁移路线（绞杀者模式，每步都能跑）

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0** | 内核骨架 + 注册表 + 事件总线 + 插件宿主；`AppServices` 改门面 | 测试全绿，行为不变 |
| **P1** | 引擎类插件：下载、投影、皮肤、LLM 网关、跨设备链路 | 设置里可切换实现；关掉某插件功能确实消失 |
| **P2** | 功能类插件：版本/实例/存档/账户/Java/整合包/诊断 | 同上 |
| **P3** | 助手类插件：Nova、Nova 执行器、**每个 Nova 工具一个 `INovaTool`**、指令助手 | 工具可单独启停 |
| **P4** | UI 贡献化：页面/卡片/分区按插件装载，外壳零硬编码，懒加载 | 启动更快；插件卸载不残留 |
| **P5** | 开放替换：外部插件可声明 `provides` 覆盖内置实现（设置里选） | 写一个第三方下载引擎插件替换内置并通过 | 

每阶段结束都要求：`dotnet build` 0 错 0 警 + 全部单测 + 实机走查。
**P0~P2 不碰 UI**，风险最低；P4 才动外壳。

## 8. 框架需求（给 Nebula / starcloud-ui，可直接转给框架 agent）

> **前提**：Nebula 是**跨软件通用引擎**（六端 × 六种风格），启动器只是它的第一个宿主，
> 后续还会有别的软件（工具类、编辑器类、客户端类）。所以下面每条都是**引擎级能力**，
> 不出现"启动器/Nova/投影/存档"这类专有名词——它们都只是宿主与插件的用法。
> 需求按"引擎该有什么"写，具体怎么用在启动器上是宿主的事。
>
> 完整清单已同步一份到 `docs/designs/2026-10-15-nebula-engine-requirements.md`
> （放这边方便两个仓库互相引用；权威内容以本节为准）。

### 8.0 现状与本需求的边界（先对齐认知，避免重复劳动）

Nebula 已有：分层与依赖方向（ADR-001，L0–L5 单向向下、core 禁平台头）、
便携 WinRT 子集（L0）、布局 / 文本 / 材质 / 风格自适应（L1–L2）、
渲染抽象与 D3D11/GLES3 后端、`core/voxel`（体素 + 公共相机）、`core/skin`、
声明式 UI 方向（ADR-006 XAML 工具链）、`spec/tokens` 品牌令牌。

本需求**只补"多宿主 + 可插拔"这一块**，不重复要它已有的东西。判据：
凡是 Nebula 已经有了的（渲染、布局、文本、材质、风格、令牌、体素渲染本体），下面不再提。

### 8.1 运行时构建视图树（最重要）

宿主与插件的界面不可能编译进引擎，所以视图树必须能**运行期构造**：
创建节点/控件、设属性、绑数据、挂事件、插入/移除子树、销毁并释放资源。
两条路径都要有：声明式（XAML 子集或等价描述）与命令式（代码构建），且两者产出同一棵视图树。

> 今天内置页面走编译期 XAML、插件走声明式，两套并存。引擎要能同时承载，
> 并且让"同一份界面描述"在两种路径下渲染一致（否则移植到六端会出现两套差异）。

### 8.2 宿主装配接口（把"外壳"从引擎里抽象出去）

引擎需要一套**宿主装配接口**（谁在用引擎，谁实现这套接口）：
窗口/表面、导航宿主（提供导航容器与"当前页"切换）、文件选择、剪贴板、
系统通知/托盘、进程拉起、文件系统与网络代理策略、遥测与崩溃上报。

- 这样"用 Nebula 做启动器"和"用 Nebula 做别的软件"是同一件事，只是装配不同。
- 引擎侧只声明接口，不实现业务（拉起游戏、装整合包这类是宿主的事）。

### 8.3 页面与贡献点的动态增删 + 懒加载

- 导航项、页面、卡片、分区、浮层必须能**运行期增删**，且不触发整窗重建或全量重排。
- **导航项与页面工厂分离**：导航项可先出现，页面第一次点进去才创建（懒加载）。
- 页面关闭要能真正释放（视图树 + GPU 缓冲 + 事件订阅）；否则卸载功能模块会泄漏。
- 贡献点需支持 priority 排序与"查询某容器现有挂载位"，供插件声明插入位置。

### 8.4 插件可用的服务解析（插件内 DI）

宿主向引擎与插件**注入**一个服务解析器（构造注入或上下文注入均可），
插件内按**契约/能力**取用，不接触宿主单例。理由：
插件与宿主生命周期不同，静态单例会导致卸载残留、多实例冲突、测试无法隔离。

引擎侧只需要提供"注入与解析"的**机制**；契约长什么样是宿主的事（不要在引擎里写死业务契约）。

### 8.5 插件装载与生命周期（引擎只提供机制）

引擎可提供：模块描述（id/kind/依赖/能力/激活时机）、依赖拓扑与循环检测、
激活/停用、激活耗时上报、按能力查提供者、配置分区读写、权限声明与裁决**挂载点**。

> 引擎**不要**实现插件系统本体（沙箱、脚本运行时、权限模型是宿主的领域）。
> 引擎只需保证：视图与资源可被正确创建与释放（8.1/8.3），并给出可插拔的资源与能力边界。
> 宿主可以选择用"进程内插件"或"进程外服务"两种形态，引擎都能承载。

### 8.6 错误隔离

单个功能/插件的视图抛异常、渲染失败、甚至原生崩溃**不能拖垮宿主**：
per-contribution 的错误边界、失败时降级为占位视图并上报、其余界面照常。

### 8.7 令牌与主题（只读 API + 变更通知）

插件/自绘 UI 查当前风格（风格自适应结果）的颜色/圆角/阴影/动效令牌，
并提供**只读令牌访问 + 风格/主题变更通知**；自绘内容不许硬编码颜色。
（`spec/tokens` + `core/style` 已有，这一条是把它**开放给外部代码**。）

### 8.8 动效档位与降级

宿主可设置"动效档位"（如最少 / 较少 / 均衡 / 全部）与全局开关；
引擎把它作为**能力查询 + 转场工具**暴露，插件/自绘动画按档位自动降级
（最低档只保留基本切换）。无障碍（减少动态效果）同样走这个档位。

### 8.9 异步与取消

视图/页面的创建与销毁带明确取消令牌；后台取数在页面关闭时必须能取消。
引擎的异步原语（六端一致）供宿主与插件共用。

### 8.10 多语言

引擎提供本地化查询 + 语言切换通知；文案可由宿主/插件注入。
插件不自己搞一套（启动器已有 zh-CN / en-US，引擎只提供机制）。

### 8.11 启动与装载时序

- 宿主提供"能力注册表"（启动期登记）与"磁盘清单"（运行期发现），合并成一张模块表。
- 支持 `eager`（启动激活）与 `lazy`（首次用到激活）两种时机；引擎上报激活耗时，便于定位启动变慢。

### 8.12 体素/皮肤模块的宿主化（现有能力的对接）

`core/voxel`、`core/skin` 已是引擎级模块。宿主化需要：
把"模型/几何/纹理解析、相机控制、交互（轨道/第一人称）"作为**可插拔的宿主侧策略**注入，
引擎只负责渲染与帧循环（现状 `camera.h` / `scene.h` 已朝这个方向）。
其它软件若要做体素预览（地图、模型查看器、数据可视化）直接复用，无需引擎改动。

### 8.13 明确**不**需要的（避免框架替宿主背业务）

- 不需要引擎实现插件沙箱/脚本运行时/权限模型（宿主领域）。
- 不需要引擎内置任何业务契约（下载、账户、版本等都是宿主插件的契约）。
- 不需要引擎知道"启动器"这个概念（它只认识宿主装配接口，见 8.2）。

### 8.14 优先级

| 优先级 | 需求 | 不做的后果 |
|---|---|---|
| P0 | 8.1 运行时视图树 / 8.3 动态增删+懒加载 / 8.4 服务注入 | 功能无法插件化（内置功能永远比插件少一档） |
| P1 | 8.2 宿主装配接口 / 8.6 错误隔离 / 8.8 动效档位 | 框架只能服务一个软件；崩溃会连坐 |
| P2 | 8.7 令牌开放 / 8.10 多语言 / 8.9 异步取消 | 插件界面风格不统一、无法国际化 |
| P3 | 8.12 体素/皮肤宿主化 / 8.11 装载时序 | 这两块跨软件复用受阻；启动慢难定位 |

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 重构把发行版搞崩 | 绞杀者模式 + 每阶段全绿；P0~P2 不碰 UI |
| 契约设计错，越改越痛 | 契约按"能力"切（能换实现才算契约），先上 3 个引擎插件验证再铺开 |
| 内核悄悄长出功能 | 代码评审判据：内核里出现具体功能名就是 bug |
| 插件卸载残留 | 卸载用例纳入单测：激活→注销→再激活，贡献点与事件订阅数量必须回到基线 |
| 外部插件越权 | 沿用 `plugin-spec-v2` 的权限白名单 + 风险分级，不新造一套 |
