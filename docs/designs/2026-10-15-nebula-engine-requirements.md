# 引擎需求：Nebula 需要的「多宿主 + 可插拔」能力

> 2026-10-15 · 来自 Starcloud Minecraft Launcher 的插件化改造（宿主侧视角）。
> 权威内容见 `docs/designs/2026-10-15-kernel-plugin-architecture.md` §8；本文是同一份清单的独立副本，
> 放在两个仓库里方便互相引用。**引擎是跨软件通用引擎，启动器只是第一个宿主**，
> 因此下面每条都是引擎级能力，不含任何业务专有名词。

## 为什么提这个需求

宿主要把"本体功能"（下载引擎、版本管理、投影预览、助手等）全部变成**可插拔**的模块，
且同一套机制还要服务后续别的软件。这对引擎的要求不是"加个插件功能"，
而是"**让宿主能把界面与能力拆开**"。

## 现状与边界（避免重复劳动）

Nebula 已有：分层与依赖方向（ADR-001）、便携 WinRT 子集、布局/文本/材质/风格自适应、
渲染抽象与 D3D11/GLES3 后端、`core/voxel` + `core/skin` 两个引擎级渲染模块、
声明式 UI 方向（ADR-006）、品牌令牌（`spec/tokens`）。

本需求只补"多宿主 + 可插拔"，不重复要已有能力；判据是已有的一律不提。

## 需求（按优先级）

### P0（不做的后果：功能无法插件化）

**N1. 运行时构建视图树**
宿主与插件的界面不能编译进引擎，必须能运行期创建/设属性/绑数据/挂事件/插入/移除/销毁。
声明式（XAML 子集或等价描述）与命令式（代码）都要有，且产出同一棵视图树。

**N2. 页面与贡献点的动态增删 + 懒加载**
导航项/页面/卡片/分区/浮层运行期增删且不整窗重建；导航项与页面工厂分离（懒创建）；
页面关闭真正释放（视图树 + GPU 资源 + 订阅），否则模块卸载泄漏；
贡献点支持 priority 排序与"查询现有挂载位"。

**N3. 宿主向引擎/插件注入服务解析器**
机制即可（构造注入或上下文注入）；插件按能力取用，不接触宿主单例——
静态单例会导致卸载残留、多实例冲突、测试无法隔离。
**契约定义留在宿主，不进引擎。**

### P1（不做的后果：框架只能服务一个软件；崩溃连坐）

**N4. 宿主装配接口**
引擎需要宿主实现的一套接口：窗口/表面、导航宿主、文件选择、剪贴板、系统通知/托盘、
进程拉起、文件系统与网络代理策略、遥测/崩溃上报。引擎只声明接口，不实现业务。

**N5. 错误隔离**
单个模块的视图抛异常/渲染失败/原生崩溃不能拖垮宿主：per-contribution 错误边界、
失败降级为占位并上报、其余界面照常。

**N6. 动效档位与降级**
宿主可设置动效档位（如最少/较少/均衡/全部）与全局开关；引擎暴露档位查询 + 转场工具，
自绘动画按档位自动降级；无障碍"减少动态效果"走同一档位。

### P2（不做的后果：风格不统一 / 无法国际化）

**N7. 令牌与主题的只读访问 + 变更通知**
把 `spec/tokens` + `core/style` 开放给外部代码查询；风格/主题变更时通知订阅方；
自绘内容不许硬编码颜色。

**N8. 多语言**
本地化查询 + 语言切换通知；文案由宿主注入，插件不自己搞一套。

**N9. 异步与取消**
视图/页面创建销毁带取消令牌；后台取数在页面关闭时必须能取消；六端一致的异步原语。

### P3（不做的后果：现有渲染模块跨软件复用受阻）

**N10. 体素/皮肤模块的宿主化**
`core/voxel`、`core/skin` 已是引擎级模块。把"模型/几何/纹理解析、相机控制、
交互（轨道/第一人称）"做成宿主可注入的策略，引擎只负责渲染与帧循环。
其它软件（地图、模型查看器、数据可视化）直接复用，无需引擎改动。

**N11. 启动与装载时序**
宿主提供"能力注册表"（启动期登记）+ 磁盘发现，合并为一张模块表；
支持 eager/lazy 激活；引擎上报激活耗时，便于定位启动变慢。

## 明确**不**需要（不要替宿主背业务）

- 不需要引擎实现插件沙箱/脚本运行时/权限模型（宿主领域）。
- 不需要引擎内置任何业务契约（下载、账户、版本、投影等都是宿主契约）。
- 不需要引擎知道"启动器"这个概念，只认识 N4 的宿主装配接口。

## 宿主侧能提供的对接

- 宿主可同时用"进程内插件"与"进程外服务"两种形态，引擎都能承载；
- 宿主会给出本宿主的挂载位清单（导航项/页面/卡片/分区…），但**框架不需要知道它们叫什么**。
