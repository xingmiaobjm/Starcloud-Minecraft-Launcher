# 启动器下载 P2P 加速 设计

日期：2026-10-14
状态：M1 已实现（局域网同账号对等复用；swarm 协议位已定义）
关联：`2026-10-14-cross-device-sync-design.md`（共用设备链路）

## 1. 目标

下载游戏（原版 jar / 库 / 资源 / Mod / 整合包文件）时，优先从**同 Starcloud ID 的局域网设备**获取已有文件，只对两端都没有的部分走公网多源下载——典型场景：台式机装好的整合包，笔记本再装一遍，库文件（数百 MB）直接局域网秒传。

**非目标（M1）**：跨账号 / 跨公网的 swarm 分发（BT-like）。协议位已定义（§5），需要云端 tracker 与激励机制，M2 评估。

## 2. 架构：插在现有管线的「第三个源」

现有下载管线已有两层复用，P2P 是它们的自然延伸：

```
DownloadBatchAsync
  ① 去重（同目标已存在 → 跳过）
  ② LocalFileReuse（本机其他实例已有同 SHA1 文件 → 本地复制）
  ③ PeerFileReuse（★新增：局域网同账号设备已有同 SHA1 文件 → 网内拉取）
  ④ 多源 HTTP（镜像竞速 / 分片 / 断点续传，原路径不动）
```

- **安全线与本地复用完全一致：只认 SHA1**。对端返回的字节流校验不过就当没有，静默回退公网下载。
- 开关 `p2p_download_enabled`（默认开）；关闭时 ③ 整体跳过，零开销。
- 对端数据面就是 DeviceLink 的 TCP 服务（`p2p.has` / `p2p.fetch`），鉴权同握手 HMAC——**只从自己账号的设备拿文件**，不引入第三方节点，天然规避投毒与版权分发问题。

## 3. 对端查找：按需探测，不做全库哈希

对端**不预先计算全库哈希**（几百 GB 扫不动）。协议按需进行：

1. 下载方持有一个待补文件 `(dest, sha1, size)`；
2. 向在线对端发 `p2p.has {sha1, size}`；
3. 对端在本机文件索引（LocalFileReuse 同源的文件名/大小索引，不算哈希）里找候选，**现场计算候选文件 SHA1**（候选只有个位数个，单文件哈希毫秒~秒级，且结果缓存）；
4. 命中回 `ok` → `p2p.fetch {sha1}` 流式拉取（8 字节长度前缀）→ 下载方 SHA1 校验 → 落地 `.sc-tmp → rename`。

并发：`p2p.fetch` 单对端串行 + 多对端并行，与整体下载并发共用信号量预算，避免把 Wi-Fi 打满影响同步。

## 4. 命中报告

每次命中在调度中心进度与日志中标注来源 `P2P ← 设备名`，用户能看见加速来自谁；未命中完全静默（零打扰）。

## 5. M2 预留：公网 swarm

- Tracker：星云网关 `/v1/p2p/announce`（仅汇报「哪些账号在拿同一 sha1 集合」，不参与数据面）；
- 数据面：账号间 TLS + 令牌评分 + 分块（1 MiB）哈希树校验；
- 激励：积分制（上传量记入账号），防女巫靠 Starcloud ID 实名；
- **协议位**：`p2p.has/fetch` 的帧格式已按 (sha1, size, offset) 设计，公网化只需加块索引命令，不动帧结构。
