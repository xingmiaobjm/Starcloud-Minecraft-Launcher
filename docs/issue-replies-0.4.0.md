## issue #6

**标题**：对于大型整合包，优化导入速度，并自动化特殊启动方式的参数配置

**回复正文（从下一条分隔线开始复制）**

---

三个问题都定位到了，根因如下：

### 1. 1.7.10 Forge 安装 404

Forge 的 maven 坐标有**两种命名**，而且同一大版本内都不统一。逐个探测结果：

| MC 版本 | 两段式 `{mc}-{build}` | 三段式 `{mc}-{build}-{mc}` |
| --- | --- | --- |
| 1.7.10 | 404 | 200 |
| 1.8.9 | 404 | 200 |
| 1.8 | 200 | 404 |
| 1.6.4 | 200 | 404 |
| 1.7.2 | 200 | 404 |
| 1.12.2 | 200 | — |

之前只拼两段式，所以 GTNH 这种 1.7.10 实例必然 404。现在会按「两段 → 三段」依次尝试，全部失败才报错，并在错误信息里列出已尝试的坐标。

### 2. 大型 MultiMC 包导入未响应

根因是打开 zip、格式探测、遍历包内全部条目、统计体积这几步是**同步**执行在 UI 线程上的。GTNH 这种几万条目的包必然卡住数秒。

已把这整段挪到后台线程，导入期间界面不再无响应。

### 3. Cleanroom / lwjgl3ify

- `lwjgl3ify` 本身是 mod 加版本 JSON 里的启动参数，导入整合包时会跟着走，不需要额外安装
- `Cleanroom` 之前只支持启动、不支持安装。现在接上了官方 installer（`installClient` 静默安装）：缺 Cleanroom 时会先补 1.12.2 原版，再跑安装器，最后扫描版本目录确认实际装出的版本

### 另外顺带修的两处

这两处都会影响你提到的这类实例：

- **多层继承时的库顺序**：子版本库必须排在父版本之前。Java 8 按 `cp` 顺序取第一个同名类，顺序反了加载器就覆盖不了原版类
- **重复启动参数**：重复的 `width` / `uuid` 类参数是两个一起失效，不是后者生效；现在会按语义整理（游戏参数后值覆盖、JVM 参数仅在键值全同时去重）

### 关于本 issue

这些修复会随 **0.4.0 同步发布**。届时请用正式版复测 GTNH 的导入和 1.7.10 Forge 安装。

**我们会在 0.4.0 发布后等待你的复测结果，再关闭本 issue。**

复测若仍有问题，麻烦附上 `%APPDATA%\starcloud-launcher\logs\launcher.log` 中带 `[forge]`、`[modpack]`、`[launch]` 的行，这些路径现在都有详细日志。

## issue #7

**标题**：支持使用系统代理设置绕过可能存在的限速/被墙问题

**回复正文（从下一条分隔线开始复制）**

---

已加上。先说明现状：主下载通道其实**一直是跟随系统代理**的（HTTP handler 默认行为），只是没有可见的开关，用户既没法确认也没法改。极端网络下（TUN 劫持、加速器、公司代理）确实会出现你截图里的不稳定。

现在「设置 → 下载」新增两项：

- **下载代理**：`跟随系统代理`（默认）/ `直连（不用代理）` / `自定义代理`
- **代理地址**：选择「自定义代理」时生效，例如 `http://127.0.0.1:7890`

行为说明：

- 改完**立即生效**，不需要重启启动器
- 局域网与 P2P 通道恒走直连，不受此设置影响（内网通信走代理反而连不上）
- 地址格式非法时会退回「跟随系统代理」并写日志，不会因为一个填错的值让下载整体失败

### 关于本 issue

这项会随 **0.4.0 同步发布**。

**我们会在 0.4.0 发布后等待你确认效果，再关闭本 issue。**

建议的验证方式：

- Clash 系统代理模式：先用「跟随系统代理」
- TUN 模式：可对比「直连」与「跟随系统代理」的速度

反馈时麻烦附上 `%APPDATA%\starcloud-launcher\logs\launcher.log` 中带 `[download]` 的行，可以看到每个文件实际使用了哪个源、传输了多少字节。
